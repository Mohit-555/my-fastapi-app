# 18 — Scalability

---

## Current System Capacity

The production server is a 2GB RAM Ubuntu instance running:
- Gunicorn with multiple workers
- PostgreSQL
- Redis
- Nginx

**Estimated device capacity today:**
- 10–50 gateways sending data every 5 seconds
- ~5,000–25,000 telemetry rows inserted per minute
- Real-time dashboard for ~50 concurrent users

Beyond this, the system shows the symptoms observed: OOM kills, DB connection exhaustion, alert processor lag.

---

## CURRENT SYSTEM — Bottlenecks

### 1. Database Write Bottleneck

Every telemetry row = one `INSERT` into `telemetry` table. At 50 gateways each sending 10 parameters every 5 seconds:

```
50 gateways × 10 params × (60/5) packets/min = 6,000 rows/minute = 100 rows/second
```

PostgreSQL can handle ~10,000 simple INSERTs/second on modest hardware. At 100 devices sending 10 parameters, this is fine. At 1,000 devices: 10,000 rows/second — at the limit. At 10,000 devices: 100,000 rows/second — PostgreSQL on a single machine will fail.

**Root cause:** Every row is committed individually per webhook request. Batching (accumulating rows and committing in groups of 500) would improve this 10×.

### 2. Alert Processor — Single-Threaded Bottleneck

The alert processor processes 100 rows per 5-second cycle. Maximum throughput: **1,200 rows/minute**.

If ingestion produces 6,000 rows/minute, the `is_processed=False` backlog grows at 4,800 rows/minute. After 1 hour: 288,000 unprocessed rows. Alert latency grows linearly. Alerts may arrive hours late.

**Root cause:** Polling-based, single async task, no parallelism across rows.

### 3. Memory — Multi-Worker Startup

Each Gunicorn worker imports all of FastAPI + SQLAlchemy + all routers. At startup, each worker also runs migrations and seeding (before the OOM fix). With 4 workers on a 2GB machine, each worker needs ~200MB. Database migrations add another 100MB spike → OOM.

**After the fix** (`RUN_STARTUP_SEEDING` flag): Workers boot lightweight (~80-100MB each). 4 workers = ~400MB. Healthy margin on 2GB.

### 4. Redis — Per-Process Fallback

With Redis unavailable and multiple workers, each worker has its own in-memory cache. A request hitting Worker 1 sees data written by Worker 1. The same request hitting Worker 2 sees nothing. Inconsistent state.

### 5. WebSocket — Connection Count

The `ConnectionManager` stores all WebSocket connections in a Python dict. With thousands of concurrent WebSocket clients, this consumes memory and the broadcast loop is O(N) for N clients. Broadcasting one telemetry update to 1,000 connected clients takes 1,000 serial `send_text()` calls.

### 6. Maintenance Mode — In-Memory

Maintenance mode state is per-process. With multiple workers, activating maintenance mode via one HTTP request hits one worker and updates that worker's in-memory state. Other workers don't see it. Alerts may still be generated by other workers.

---

## SCALING ANALYSIS: 10 → 1,000 → 100,000 Devices

### 10 Devices (Current, Working)
- 100 rows/minute → trivial for PostgreSQL
- Alert processor keeps up easily
- Single server, 2 workers, Redis optional
- No bottlenecks

### 1,000 Devices (Near-Term Scaling)
- 10,000–60,000 rows/minute → PostgreSQL starts to strain
- Alert processor backlog grows — latency 5-30 minutes
- Redis becomes mandatory (fallback breaks consistency)
- Need: DB read replicas, alert processor parallelization
- Memory: 4 workers × 100MB = 400MB — fine on 4GB server

### 100,000 Devices (Enterprise Scale)
- 1,000,000–6,000,000 rows/minute → single PostgreSQL impossible
- Alert processor needs hundreds of parallel workers
- WebSocket broadcasting needs message broker (Redis pub/sub or Kafka)
- Redis single node becomes bottleneck
- Need: Full architectural redesign

## POSSIBLE FUTURE ARCHITECTURE

### Layer 1: Ingestion Scale-Out

**Current:** Webhook handler writes directly to PostgreSQL.

**Future:** 
```
Gateway → Nginx → FastAPI webhook → Kafka/Redis Stream → DB writers (pool)
```

- FastAPI webhook just publishes to Kafka. Returns 202 in <1ms.
- Separate consumer pool writes to PostgreSQL in batches of 500–1000 rows.
- Kafka retains messages — no data loss if DB is slow.

### Layer 2: Alert Processing Scale-Out

**Current:** Single asyncio task, polling, 100 rows/5s.

**Future:**
```
Telemetry written → Kafka message → N alert worker processes
```
Each worker picks up messages, evaluates, writes alerts. Workers are stateless — any worker can handle any row. Scale horizontally.

Replace `is_processed` polling with Kafka consumer groups. Each consumer group gets a partition of telemetry. No database polling needed.

### Layer 3: Database Scale-Out

**Current:** Single PostgreSQL instance.

**Future options:**
1. **Read replicas:** All `SELECT` queries go to replicas. Only writes hit the primary.
2. **TimescaleDB:** PostgreSQL extension for time-series. Automatic partitioning by time. Compression. `DISTINCT ON` queries become much faster.
3. **Table partitioning:** Partition `telemetry` by month. Old partitions can be archived or dropped without affecting the active partition.

### Layer 4: WebSocket Scale-Out

**Current:** Connections tracked in-memory per process. `broadcast_to_station()` iterates all connections.

**Future:**
```
FastAPI instances (stateless) → Redis pub/sub ← alert_processor publishes
```

When an alert is generated, alert_processor publishes to `rdpms:station:LKO:alerts` Redis channel. All FastAPI instances subscribed to that channel broadcast to their local WebSocket connections. No direct coupling between alert processor and web server.

### Layer 5: Cache Scale-Out

**Current:** Single Redis node, in-memory fallback per worker.

**Future:**
- Redis Sentinel for high availability (auto-failover)
- Redis Cluster for horizontal scaling
- Read-through cache: if Redis misses, query DB and populate cache

## Monitoring Bottleneck Indicators

| Symptom | Root Cause |
|---|---|
| `WHERE is_processed=False COUNT(*)` growing | Alert processor can't keep up |
| DB CPU > 80% sustained | Write or read bottleneck |
| Worker OOM kill | Per-worker memory too high (check startup hooks) |
| Alert latency > 5 minutes | Alert processor backlog |
| Redis memory growing unboundedly | TTL not set or too long |
| WebSocket clients disconnecting randomly | Heartbeat timeout (60s) |
| 429 errors on valid requests | Rate limiter per-worker (memory mode) |

## Current vs Future Summary

| Aspect | Current | Future (1,000+ devices) |
|---|---|---|
| Ingestion | Direct DB write | Kafka → batch DB write |
| Alert processing | Polling asyncio task | Kafka consumers (horizontal) |
| Database | Single PostgreSQL | TimescaleDB + read replicas |
| Cache | Redis + memory fallback | Redis Cluster + Sentinel |
| WebSocket broadcast | In-process iteration | Redis pub/sub fan-out |
| Maintenance mode | In-memory per process | Redis key per asset |
| Alert deduplication | In-memory per process | Redis atomic operations |
